One command, six steps, then it stops cleanly

Each session works within a budget: 4 work items, 3 hours or 10 bugs filed by default. Then it tells you to /clear and run it again. Nothing it knows is kept in the chat.

  1. Orient

    Reads the master QA plan, the last session's log, the backlog and the bug ledger.

  2. Sync

    Fetches your app repos read-only, pulls the test cases and specs, and finds bugs waiting for retest.

  3. Work out the change impact

    Reads the real diffs since the last recorded commit and decides which test cases to add, update or retire.

  4. Revise the plan

    Puts change work first, then retests, then regression, and tells you in a few lines what it will do.

  5. Do the work

    Designs missing cases, runs suites in a real browser, files bugs with screenshots and a duplicate check, and retests fixes.

  6. Close and log

    Reviews its own work, updates the plan and ledger, commits locally, and records where the next session starts.

Everything it knows lives in plain files

Your plan, results and bug history stay in your project as Markdown you can read, review and commit.

  • Changes are tracked by commit, not by dateEach log entry records the exact commits it compared up to, so nothing slips through between sessions.
  • Specs and builds are checked against each otherCases for a spec that hasn't shipped are marked "awaiting build". Code with no spec raises a product question, not a bug.
  • Good test design comes firstNegatives, permissions via URL and API, data isolation, boundaries, empty states and localisation, before anything runs.

Rules it follows in every session

These apply on top of your project's own rules and CLAUDE.md.

  • Tests only in your test environment, never in anything you list as off-limits.
  • Never edits, pulls, checks out, commits or pushes your app repos. It only fetches and reads them.
  • Commits test cases and state files locally. It pushes only if you turn on auto_push.
  • Prefixes everything it creates in the test environment, so test data is easy to find and clean up.
  • Keeps passwords in one git-ignored file and types them only into your test sign-in page.
  • Marks a case Pass or Fail only if it ran this session. Every Fail has a screenshot and a bug.
  • Starts only when you type /qa-session. Claude never starts a session by itself.

Questions

What do I need to use it?

Claude Code and a test environment you're allowed to test, such as staging or UAT. Local clones of your app repos and a browser tool (Claude in Chrome or the Playwright MCP) are recommended. A bug tracker is optional.

I don't have any test cases yet.

That's fine. The first sessions design them from your specs and the app's behaviour, using the ID format you choose.

Will it push or deploy anything?

No. It commits locally and pushes only the test-case repo, and only if you turn on auto_push. It never touches your app repos.

Can it test mobile apps?

It drives a desktop browser. A case that really needs a phone is marked blocked, and a suspected defect gets a label so someone can check it on a device.

Can I stop it mid-session?

Yes. It saves progress after every work item, so a session can end at any point without losing work.

Is this a subscription?

No. You pay once and keep the skill for good, with every future version included. The license is for you only, so you can't share or publish the skill.

Can my whole team use one copy?

No. One purchase covers one person. Each person who uses qa-session buys their own copy.

How do updates work?

Each new version is emailed to you and stays downloadable from your Gumroad library, as a zip. You replace the skill folder. Your config and your qa/ files live in your project, so nothing you've built up is lost.
